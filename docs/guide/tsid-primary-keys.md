# TSID 主键评估

## 结论

对 Conflua 当前的单实例 `make webapi` 开发运行和单实例 pywebview，`tsidpy==1.1.5` 生成的 TSID 可用于 SQLite 文本主键。集成用例覆盖格式、键值写入、消息与投递持久化和消息分页。使用条件是：写入同一数据库的服务实例必须避免并发共用相同发号节点。

当前 `new_tsid` 使用进程内共享生成器，默认节点固定为 `0`。生成器的线程锁能协调同一进程内的线程，但不能协调独立进程。发生数据库主键冲突时，SQLite 会拒绝写入；业务事务会回滚，不会覆盖已有记录，但请求会失败。

## 本项目的运行方式

### `make webapi`

Makefile 默认使用 `dev` profile，启动参数由 `config/config.yaml`、`.env.dev` 和环境变量共同决定。仓库中的 `config/config.yaml` 默认 `reload: false`；本次评估工作区读取到的 dev 生效值为 `reload: true`。启用 reload 时，项目的 `DevelopmentReload` supervisor 同一时刻只运行一个服务子进程，重载时等待旧进程退出后再启动新进程。因此，正常 reload 本身不会形成多个同时发号的服务子进程。

普通 Uvicorn 启动未在项目代码中指定 worker 数，默认是一个 worker。不过 Uvicorn 会读取 `WEB_CONCURRENCY`：当 reload 关闭且该变量设为大于 `1` 时，会启动多个 worker。要让多个 worker 访问同一数据库，不能直接沿用默认节点 `0`。reload 重启会重建进程内生成器，计数状态不持久化；极端情况下若重启后复用相同时间和初始计数，仍有重复可能。

开发数据库默认位于工作目录下的 `data/conflua.db`。

### pywebview

`make desktop` 启动一个 pywebview 应用进程。应用在该进程内创建一个 `conflua-api` 服务线程，Uvicorn 使用已构造的应用对象并明确设置 `reload=False`。按此启动方式，线程共享同一进程的 TSID 生成器，由生成器锁协调。

桌面数据库默认位于 `~/.conflua/data/conflua.db`。开发 API 和 pywebview 默认都绑定 `127.0.0.1:9081`，通常不能同时占用该端口；两者默认数据库路径也不同。若通过更改端口和数据库配置使两个应用进程同时写同一数据库，仍会有相同节点的多进程冲突风险。项目没有为多个并发实例自动分配节点。

## SQLite 主键压力测试

测试使用独立进程生成 ID，并逐条插入内存 SQLite 表：

```sql
CREATE TABLE pk_probe (id TEXT NOT NULL PRIMARY KEY);
```

每次 `SQLITE_CONSTRAINT_PRIMARYKEY` 拒绝均计为一次冲突。4 个进程各生成 40,000 个 ID，写入同一主键作用域：

| 节点分配 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 合计 |
| --- | ---: | ---: | ---: | ---: |
| 所有进程使用节点 `0` | 18,642 / 160,000 (11.65%) | 27,735 / 160,000 (17.33%) | 25,140 / 160,000 (15.71%) | 71,517 / 480,000 (14.90%) |
| 分配节点 `0`、`1`、`2`、`3` | 0 / 160,000 | 0 / 160,000 | 0 / 160,000 | 0 / 480,000 |

固定到同一毫秒的额外压力测试中，同节点为 21,119 / 32,768 次主键冲突 (64.45%)；使用四个不同节点为 0 / 32,768。该冻结时钟场景用于暴露重叠计数空间，不代表日常请求的冲突率。

这些比例只适用于该压力负载和同一个主键作用域，不是 `make webapi` 或 pywebview 的线上失败率。它证明多个进程共享节点 `0` 时会产生实际主键冲突；分配不同节点后，本测试样本未出现冲突。测试不能证明所有时钟回拨、进程重启或节点错误复用的情况都安全。

## 数据与顺序验证

- TSID 作为 13 字符大写文本保存；隔离表验证并发生成的 TSID 可作为主键和外键写入，并保持数字排序。
- 发布消息会持久化消息与投递的 TSID；使用相同发布标识重放时返回原消息。
- 模拟后续消息的 TSID 字符串小于前一条消息，列表和游标分页仍按消息 `seq` 返回；业务顺序不依赖 TSID 字符串顺序。事件使用 `event_id`。
- 当前项目验证器将 TSID 限定在 SQLite 有符号 64 位范围，按 TSID epoch 推算，上界时间约为 2089-09-06。达到范围边界前需要重新评估标识方案。

[TSID 集成用例](../../tests/integration/test_tsid_primary_keys.py)带有 pytest 的 `integration` 标记，不随 `make test` 运行。请在仓库根目录显式执行：

```bash
uv run --locked pytest -m integration tests/integration
```

重复主键比例压力测试是一次性临时脚本，使用内存 SQLite，不触及项目数据库。

## 使用建议

- 当前 `make webapi` 和单实例 pywebview 可继续使用 TSID；开发环境确认 reload/worker 的有效配置。
- 不要让多个 worker 或多个 Conflua 进程共用默认节点 `0` 并写入同一数据库。开发服务与桌面默认使用不同数据库，但同时启动时要注意默认端口冲突。
- 若未来需要多个进程共享数据库，应给每个同时活跃的发号进程分配协调管理、互不重复的节点 (`0..1023`)，并实现进程配置和生命周期管理；不能由每个进程随机选节点。还要单独验证重启、时钟回拨和节点回收策略。
