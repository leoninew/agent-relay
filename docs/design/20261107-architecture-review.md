# 架构审视：按消息路由职责修正范围
最后修改时间: 2026-11-07 14:11:10

## 当前结论

用户已否定上一轮审视中的范围扩张。修订 5 把会话执行管理、会话输出读取及实现细节放成消息路由的前置要求，判断不当；相关要求撤回，以本次修订 6 和[总计划](../plan/20261107-backend-from-web.md)为准。

当前职责是：持久保存聊天室消息、显式目标、实际投递和真实入队结果，并将记录可视化。成员显式发布的消息沿用普通路由；Codex 自己执行什么、有没有执行权限及如何处理审批，不属于 Relay 的路由职责。

## 对六项反馈的处理

| 用户反馈 | 当前处理 |
| --- | --- |
| 先不考虑备份、恢复 | 相关设计与演练后置，保留历史目标，不作为本轮前置或验收 |
| 不管理成员执行权限 | 撤回执行配置档、审批/用户输入处理矩阵及安全隔离前置；只保留房间、成员身份和路由目标的业务校验 |
| 单读循环是什么 | 只是 stdio 适配器读取 app-server 返回数据的一种内部写法，不是业务能力，也不需要用户决策；撤回独立架构要求 |
| 只持久化记录并可视化 | 不增加可选输出观察、普通输出扫描、后台工具完成核对；原 T06 后置并移除其对主线的阻断 |
| queue 固定，业务接口按需定义 | Codex queue 按已核验协议调用；Relay 自己的接口、工具入参和返回随对应业务需要设计，不要求创建前冻结全部未来接口 |
| 不需要发给自己 | 继续排除发布成员；撤回收件箱、发件箱和作者自查等新增建议，不以查阅问题增加自投递 |

## 仍适用的技术事实

- 本机 Codex 0.167.0 已验证独立 app-server 创建持久会话、queue 入队、忙碌时继续入队，以及显式发布工具通路。采用 Relay 管理持久会话的既有决定保留。
- queue 的成功回执仅表示入队，不表示接收者已读、已执行或已回复。相同 clientUserMessageId 重复提交会形成不同队列项，因此不能因无回复或超时自动重发。
- 话题和 @ 取并集、去重、排除发布成员，全部目标有效且实际接收人非空，才持久保存消息及投递。引用不补造目标。
- 成员只有携带明确话题或 @ 的发布进入聊天室；普通执行输出、turnId 和 final_answer 不决定路由，不主动读取这些内容来构造房间消息。

已有[协议能力证据](evidence/20261107-codex-0.167.0.json)继续保留。[队列恢复探测](evidence/20261107-codex-queue-recovery.json)只作为已发生的调查记录，不产生本轮备份/恢复任务或额外前置。

## 当前实施关注点

1. 一次发布原子保存消息、显式目标、实际投递和发布标识，避免重复落库及半条记录。
2. 向实际接收成员的 Codex queue 提交本次消息，保存匹配的回执；结果不明就如实记录 unknown，不自动重新提交。
3. Web 和 CLI 查询同一份持久记录，页面状态、数量和秒级时间对应已有事实；不虚构接收、已读或回复状态。

全部历史目标仍在总计划台账，后置事项有明确状态；不为保留历史目标继续把它们挂成当前任务的依赖。本轮仅修正文档，不修改产品代码、不追加协议探测。
