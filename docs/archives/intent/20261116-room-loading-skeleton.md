## Background / 背景

用户提出在加载聊天室时引入骨架屏，随后要求先核对 `docs/reka-ui-llms.txt`，再通过 SpecFlow 记录任务，并明确“从整体到细节地实施，不要求一步到位”。首次记录意图与候选任务后，用户授权先实现 T01；当前按同名总计划逐轮实施和交付。

已核对的仓库事实（代码基线 `396f703`）：

- `web/src/domains/room/RoomPage.vue` 在没有 snapshot 时展示居中的图标、文字和加载指示，数据返回后才挂载整个工作台。
- `openChannel` 会删除目标频道的 snapshot，因此返回已访问频道也会重新加载，不能将现状当作已有可直接显示的频道缓存。
- `loadRoom` 被初次加载、搜索、筛选、刷新及页面重新激活等场景共用；`MessageTimeline.vue` 当前在 `loading` 时隐藏整个消息列表。`loadOlder` 已有独立加载状态和滚动位置恢复。
- `RoomWorkbench.vue` 已有面板折叠偏好、可调整宽度及响应式布局：720px 及以下导航改为抽屉，1150px 及以下详情改为抽屉。骨架需要沿用这些边界。
- 本地 Reka UI 文档与已安装的 `reka-ui@2.11.0` 没有 Skeleton 或 Shimmer 导出；Progress 提供进度指示，不能直接提供聊天室占位布局。
- 项目已有主题变量、`AppLoading` 的状态提示语义，以及工作台内的 `prefers-reduced-motion` 样式。

## Goals / 目标

- 首先让用户在初次进入和切换聊天室／频道时看到接近真实工作台的占位结构，减少加载前后的布局变化。
- 随后区分初次加载、同一查询刷新、新查询、历史分页及实时更新，按场景保留已有内容或展示局部占位。
- 最后完善短请求闪烁、主题、动效和可访问性细节，每轮具备可检查的独立交付。
- 复用现有 Vue、CSS、Reka 工作台布局和主题体系，保持草稿、引用、焦点与滚动行为可靠。

## Non-goals / 非目标

- 本功能不承担 API 性能优化、后端接口或数据库改造，也不以骨架屏承诺缩短真实请求耗时。
- 不将频道缓存策略重构与骨架屏绑定；是否保留跨频道快照需要另行评估查询条件及失效边界。
- 不扩展为全站加载样式改造，不覆盖应用挂载前、项目菜单和所有业务弹窗的加载体验。
- 不新增组件库、动画依赖或浏览器测试框架。
- 实施按 T01、T02、T03 逐轮推进；三个节点均已接受。用户最新明确任务无问题并要求完成验收文档，整体 Verification 见同名报告；不进行 UI 测试或自动 Git 提交，开发服务器由用户管理。

## User stories / scenarios / 用户故事 / 场景

- 初次进入聊天室时，用户先看到符合当前视口和面板折叠偏好的工作台轮廓，再看到真实内容。
- 切换聊天室或频道时，目标范围尚未加载的数据使用骨架占位，快速连续切换不会显示旧目标的结果。
- 同一查询下刷新或重新激活页面时，用户继续阅读已有消息，草稿与当前位置保持，仅出现局部忙碌提示。
- 搜索或切换话题／成员筛选时，导航和输入区保留，消息区体现新查询正在加载，旧结果不会被误认为新条件的结果。
- 加载历史消息时，已有消息继续可见，局部加载反馈不会导致滚动跳动。
- 请求成功但没有数据、搜索没有匹配以及请求失败时，用户获得相应的空状态或错误与重试入口。
- 暗色主题、窄屏、键盘和辅助技术用户都能理解加载状态，减少动态效果设置得到遵循。

## Acceptance criteria / 验收标准

- A01：初次进入和切换聊天室／频道的无 snapshot 加载阶段展示工作台骨架，包含当前布局下可见的导航列表、消息、输入区轮廓及详情／队列区域；沿用面板折叠偏好和响应式断点，无额外横向溢出。
- A02：快速连续切换及请求取消时，骨架与真实内容均对应当前房间和频道；旧请求的完成或失败不覆盖新目标的状态。
- A03：同一查询刷新和页面重新激活时，已有消息保持可见，局部状态提示更新过程；刷新失败仍可查看旧内容并重试，保留滚动位置及草稿。
- A04：搜索或切换话题／成员筛选时，仅消息区域进入新查询加载状态；导航及输入区保持，旧结果不作为新查询结果展示。
- A05：历史分页沿用局部加载与滚动恢复，实时事件更新不触发整页骨架。
- A06：空频道、无搜索结果、频道不可用与加载失败具有明确状态；加载结束后骨架及忙碌状态能退出，失败时有适用的重试入口。
- A07：骨架使用现有主题变量，适配明暗主题与减少动态效果设置；装饰占位不进入焦点顺序和读屏内容，由容器提供单一、可理解的加载提示。
- A08：短请求的显示策略以减少闪烁为目标，真实内容就绪后立即呈现；若使用延迟，切换、取消及卸载时清理旧定时器，不人为设置最短等待时间。
- A09：骨架阶段不挂载用于占位的真实编辑器；加载和内容切换不丢草稿、引用或待确认发布信息，不产生额外发送和意外焦点跳转。
- A10：按各轮实际改动运行已有前端检查，记录通过、失败及未运行项；整体完成时逐项对照以上验收，不用单元检查替代界面视觉证据。

## Workload assessment / 工作量评估

工作量中等。主要交付依次是工作台骨架、加载状态衔接、体验细节与整体验收证据；职责集中在前端，预期影响 `RoomPage.vue`、`RoomWorkbench.vue` 的装配边界、`MessageTimeline.vue`、骨架组件、相关样式及必要的国际化文案。

复杂度中等。基础灰块实现简单，主要复杂性来自同一个 `loading` 覆盖多个业务场景，以及频道切换、查询条件、编辑器生命周期与请求取消之间的衔接。评审需要结合 `openRoom`、`openChannel`、`loadRoom`、`loadOlder`、生命周期监听和 snapshot 存储范围，不能只检查新组件外观。

风险中等，集中在筛选与旧消息对应关系、滚动和草稿保留、面板断点及快速切换时序。当前没有采集真实请求耗时，骨架显示延迟与占位密度需要后续体验验证。

结论：建立三个串行 task。它们各有可交付结果，便于用户按轮次体验；共享修改集中在 `RoomPage.vue` 和样式，应在同一主会话按顺序整合。正式 task 与执行登记已建立，执行依赖以同名总计划为准；下表保留意图拆分依据。

## Decisions / 决策

- 按“整体工作台骨架 → 加载状态衔接 → 视觉与体验细节”的顺序推进，允许分轮交付，不要求本轮完成所有细节。
- 使用 Vue 与 CSS 构建轻量骨架组件，复用现有 `RoomWorkbench` 布局；占位消息贴合现有作者行、标签和正文结构。
- 初次加载、新查询与已有内容刷新分别处理；空状态和错误状态继续表达真实结果。
- 键盘、读屏及减少动态效果的基础约束从首轮纳入，后续一轮再完善体验和检查。
- 进入 Plan 后按 SpecFlow 子任务协作契约记录正式依赖与交付，本意图不预先分配执行者。

## Risks / assumptions / 风险 / 假设

- snapshot 当前按房间和频道保存，消息内容还受到查询条件影响。不能直接取消快照删除来实现缓存复用，以免将其他筛选结果展示到当前条件下。
- `loadRoom` 在同步 snapshot 后仍可能继续获取选中详情或引用消息。整页骨架、消息加载及编辑器就绪的判定边界需要结合实际流程设计，不能全部机械绑定一个 `loading`。
- 另写一套固定三栏骨架可能与面板折叠及断点偏离；应复用布局，并在各轮检查结构变化。
- 骨架会改善等待时的反馈，真实网络或后端性能问题仍需独立证据定位。
- 用户自行管理服务和界面确认；agent 未执行的专项视觉检查在验收报告中明确记录，用户总体确认不等于专项测试结果。
