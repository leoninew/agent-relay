## Technical decisions / 局部技术设计

- Message 保留话题、显式 @、实际接收人和可选同房间引用；Delivery 固定 targetMemberId 和发送时 targetSessionId，初始 pending。D11 建议逐 Delivery 保存当时命中的 topicIds 和是否显式 @，不从当前订阅反推；具体展示归 T09。
- 新发布的实际目标须为活动成员且已有 T02 的可核验会话绑定。忙闲/加载状态不改变路由。既有 Delivery 的读取不再过滤成员当前 deletedAt，按持久 targetSessionId 处理；本次不增加成员重绑定或通用绑定版本功能。
- N1 仅增加提交器必需的投递领取/状态定向读写并保持短事务，外部 RPC 不持事务。资源和历史访问整体改造保留后续，不先重写全部 Store。
- 同一写事务内完成目标校验、订阅展开、去重、实际非空校验、Seq 分配、Message/目标/Delivery/幂等记录；持久事件随 T08 接入时同事务追加；任何无效目标整条回滚。N1 新序号来自写事务读取的持久最大 seq，不从列表长度推导；独立计数随访问优化后续交付。
- D03 已接受：全部目标有效后，合并话题订阅与 @、去重、排除可信发布成员，再检查实际非空；显式 @ 自己仍排除。空目标整条拒绝，保留原始显式选择用于成功消息的目标快照。控制台无绑定成员不排除任何人，不按显示名推断身份。
- 唯一约束覆盖 `(room_id, seq)`、`(message_id, target_member_id)` 和 `(room_id, caller_id, publication_id)`。成员 sender 取可信调用上下文，控制台/CLI 取已定入口身份。
- 发布请求指纹以服务接受后的正文、去重排序目标与引用计算；目标顺序不产生新意图。先检查已有发布键再看当前订阅，重放返回原发布结果；相同键不同请求 409。
- POST 成功仅表示 Relay 持久接收。新增按调用方及 publicationId 找回结果的接口；X-Request-Id 继续只用于链路排障。
- N1 接口方案：CreateMessage 增加必填稳定 publicationId；提供 GET /api/room/{roomId}/publication/{publicationId} 只读找回，身份从同一入口上下文取。控制台/Web/普通 HTTP CLI 由服务固定为控制台发布域，不接受正文 senderId/callerId；T05 以后从受控上下文提供成员发布域，不预设其 callId 格式。
- Delivery/DTO/统计统一使用 pending/submitting/queued/rejected/unknown；本节点只创建 pending，其余状态由 T04 产生。移除演示 delivered 语义，不把旧状态值转换成真实入队凭证；前后端同一整合版本直接切换。
- 完整目标中的事件后续与 T08 一起落实：采用独立持久 ID，写入与业务同事务、通知在提交后。N1 不先建持久事件基础。

1. 先固定消息、目标会话、投递和发布键的必需 schema/DTO；根目录显式 SQL 迁移，业务 Store 不迁移。事件 schema 后续接 T08。
2. 提取统一发布用例和路由函数，供 Web/CLI/成员入口复用；保留正文 #/@ 不路由规则。
3. 实现事务、幂等冲突/找回接口和持久目标快照；订阅更新和发送以数据库事务顺序确定生效关系。
4. 暴露 T04 必需的领取/结果读写并立即接真实队列，向 T09 交付发布/找回/状态。详细来源、事件、有界查询和剩余优化后续按各自范围完成。
