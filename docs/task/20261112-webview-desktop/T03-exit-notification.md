## Goal and acceptance / 目标与验收

交付用户要求的简单退出流程，对应 A05、A08。

- 取消关闭时继续运行，不发离线消息。
- 确认关闭时，如本次运行发送过管理端消息，对相关聊天室当前 Agent 各投递一次“管理端已离线。”，随后退出。
- 未发送过消息或聊天室没有 Agent 时直接完成正常关闭；通知失败记日志，不等待模型回复。

## Technical decisions / 局部技术设计

- app 启动时保存运行开始时间；通过已提交的固定人类成员消息查询本次运行涉及的聊天室，避免将草稿、失败请求和历史启动前消息计入。
- 对每个房间使用固定人类成员“你”及现有 `CreateMessage`/发布用例，直接指定当前 Agent 成员；目标不依赖界面话题筛选。无 Agent 跳过，不伪造系统成员。
- 通知内容固定“管理端已离线。”；每次已确认退出、每个房间一条，复用 publication 标识与既有结果处理，避免重复触发关闭回调造成多次发布。
- 在 API 与投递能力仍可用时完成一次正常提交尝试，检查实际提交而非只看落库；复用现有投递并保留其并发和回执语义。
- 提交后不等待 `received` 或模型回复；失败记录后继续退出。内部按既有 lifespan 收尾，不把全量待办清空或通用取消机制加入退出条件。

## Implementation outline / 实施安排

1. 建立本次运行参与发送房间的查询及通知目标选择。
2. 编排现有发布与投递，在桌面确认后调用，处理无消息、空目标和失败。
3. 验证通知获得提交机会后正常关闭，取消仍维持原运行状态。

## Checks and delivery / 检查与交付

- 使用 fake 仓储/driver 检查本次运行范围、多房间去重、Agent 目标、取消、无消息、失败及重复关闭回调。
- 单元检查发布目标、稳定 publication 标识、逐房间失败处理和确认接线；实际提交行为由用户后续真实制品验证，不增加数据库/runner 集成测试。
