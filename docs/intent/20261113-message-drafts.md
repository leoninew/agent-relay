## Background / 背景

未发送消息在编辑期间没有持久化，刷新重建 Vue 页面后会丢失。现有逻辑只对点击发送后、结果尚未确认的请求保留恢复记录；这与编辑草稿是两种不同状态。

## Goals / 目标

- 输入期间自动保留草稿，刷新同一页面并重新打开原房间后可继续编辑，无需手动保存。
- 按房间隔离，保留正文的换行和空格，以及用户已选的发送上下文。
- 与已有待确认发布恢复共存，避免重复发布或因刷新生成新的请求身份。
- 发送失败保留内容，确认成功后清理对应草稿；清空内容后不会因旧保存任务再次出现。

## Non-goals / 非目标

- 首期不承诺关标签页、退出桌面应用、换浏览器／设备或换服务地址后恢复。
- 不引入服务端草稿、数据库迁移、自动发送、后台补发、草稿历史、多版本合并或跨标签页协同编辑。
- 不恢复焦点、光标、选择范围或输入法尚未提交的候选字；已提交到输入模型的中文文字需要保留。
- 不把刷新确认弹窗作为主要保存方式；不改变现有消息发布、投递与重试的业务契约。
- 浏览器存储故障、容量不足、权限限制及缓存损坏不纳入本次开发与测试；不新增存储降级、故障提示或修复机制。
- 不增加缓存格式版本、草稿修订号或额外发送关联字段。

## Recommended strategy / 推荐策略

### 保存范围与时机

使用 sessionStorage，为每个 roomId 保存一份普通 JSON 草稿，采用独立于 `relay-publication:<roomId>` 的键，直接沿用 MessageDraft 结构。

保存正文原值、topicIds、mentionedMemberIds、capabilities、replyToMessageId。引用只保存 ID，显示信息从房间数据或已有消息查询能力恢复；继续沿用既有发送校验。

当前正文限制为 6000 字符，在编辑模型更新时同步写入本房间的小记录，不引入防抖窗口，不依赖卸载保存。

这里的触发点是原生 `input` 经组件更新 Vue 模型后的变化，而不是通常在失焦时触发的 DOM `change`。实现可使用同步 watcher 或模型 setter；当前 AppInput 在 `compositionend` 才提交输入法文字，因此首期保存已提交的中文，不额外捕获尚未提交的候选字。

### 恢复与失效数据

恢复优先级为：有效的待确认发布请求 → 当前标签页中的编辑草稿 → 空白编辑器。恢复只填入输入区，不发送网络写请求，不为普通草稿生成 publicationId。

应在确认房间身份后、编辑器用空值覆盖草稿前完成读取；收到有效房间元数据后再核对话题、成员和引用。失效接收对象不得静默替换为其他对象，提示用户检查；正文保留。引用已删除时，普通草稿可移除该引用并提示；网络暂时不可用时不要据此判定引用已删除。

待确认发布请求是已冻结的请求：保留 publicationId 与原始 payload，继续已有的用户主动核对流程。不得被普通草稿、恢复校验或后台元数据刷新改写成另一个待发送请求。

### 保存与清理边界

| 事件                           | 建议行为                                                                                   |
| ------------------------------ | ------------------------------------------------------------------------------------------ |
| 修改正文、发送目标、能力或引用 | 更新对应房间的编辑草稿；取消引用也需要保存                                                 |
| 切换房间或刷新                 | 恢复本房间草稿，不串到其他房间；不自动调用发送                                             |
| 点击发送                       | 保留草稿，同时沿用独立待确认请求及 publicationId                                           |
| 明确发送失败                   | 保留或恢复为可编辑草稿，允许用户修正后再发送                                               |
| 超时、断网、结果未知           | 保留冻结请求与草稿，继续原核对入口，不自动创建新 publicationId                             |
| 确认发送成功                   | 清除本次发送房间的草稿和待确认记录，不影响其他房间                                         |
| 正文被清空                     | 清除已保存正文；保留仍在编辑的引用／能力等有效上下文。仅有默认话题选择时不必视为待发送消息 |
| 删除房间成功                   | 清除该房间草稿，不在删除失败时清理                                                         |
| 清空房间历史                   | 建议保留未发送正文，校验失效引用和接收对象；历史消息清理不等于用户丢弃草稿                 |

现有发送及待确认期间编辑区已锁定；沿用这一行为，按发送所属房间清理，并处理好同步保存与 reset 的顺序即可。不增加草稿修订号或发送关联机制。

## User stories / scenarios / 用户故事 / 场景

- 用户写入多行中英文、选择话题和成员后立即刷新，重新打开同一房间能继续编辑。
- 用户分别在两个房间编辑草稿，往返或刷新后各自恢复；同一房间的两个独立标签页不互相覆盖后续输入。
- 用户引用一条消息并选择能力，刷新后仍可辨识发送上下文；引用失效时保留正文并提示处理。
- 用户点击发送后网络超时并刷新，仍看到待确认入口，继续使用原请求身份核对，不自动重发。
- 用户发送成功后刷新，已发送正文不重新填入；发送失败后刷新仍能继续编辑或核对。

## Acceptance criteria / 验收标准

- A01：已提交到编辑模型的正文、换行和空格在同源同标签页刷新后恢复；输入后立即刷新和输入法提交后刷新都需检查。
- A02：不同 roomId 的草稿隔离，独立标签页的后续编辑互不覆盖；房间切换前后引用及能力上下文可恢复。
- A03：话题、提及、能力与引用按现有契约校验；恢复不在元数据未加载时误清选择，不默默改变发送目标，失效引用不清除正文。
- A04：普通草稿恢复不发送消息、不分配 publicationId；待确认请求优先恢复并保留原 ID、payload 和主动核对行为。
- A05：明确发送失败和结果未知均保留可恢复内容；确认成功清理发送所属房间的草稿，刷新不复活已发送内容，不影响其他房间。
- A06：清空正文、取消引用、发送后 reset、删除房间及清空历史遵循明确清理规则；删除失败不丢草稿。

- A08：保存与恢复不刷新路由、重建额外业务订阅或引入后端写接口；Node 替身检查与真实浏览器／WebView 刷新证据分别记录。

## Risks / assumptions / 风险 / 假设

- 浏览器可能自行恢复标签页会话，sessionStorage 并非“关闭就一定删除”；本方案只承诺正常可用存储下的同源刷新范围。
- 主机名、端口、浏览器配置或 WebView 实例变化会影响存储可见性，不能将固定 WebView 用户目录等同于 sessionStorage 跨进程持久化。
- 正文属于浏览器本地可读内容，避免复制到业务日志或成功提示；不因此增加服务端数据副本。
- localStorage 的“最后一次写入获胜”与成功后无条件删除可能覆盖其他标签页的新草稿；升级保存范围时需要单独解决版本与编辑者归属，不能承诺自动同步没有冲突。
- 浏览器或进程异常终止时，不承诺尚未提交到模型的输入法缓冲或浏览器尚未落盘的数据。
