## Background and goals / 背景与目标

- 用户要求根据当前业务抽象和实现反推 MCP 与“SKU”的改进项；评估按 Skill 理解，用户随后显式调用 SpecFlow 要求记录任务，并说明将交由其他会话处理。
- 基线为 `2d5d63158573316d59ce316c9b12ea5ab07101c7`。当前 Room、Topic、Member、Message、Delivery 模型已经支持范围队列、软删除、相关成员筛选与关键词查询；MCP、共用客户端及协作 Skill 尚未完整跟进。
- 补齐 MCP/CLI 的队列能力，修正查询说明与实际语义的偏差，明确历史投递与有效队列的区别。
- 将减少无效沟通、识别延迟或过时消息等协作规则纳入唯一 Skill 源码；为实际投递增加稳定的消息定位信息，使规则可以依托已有上下文工具执行。

## Non-goals / 非目标

- 不新增任务实体、认领锁、任务完成状态、广播资源或权限系统；不改变现有路由和成员可见上下文规则。
- 不更改前端详情、Hover、列表截断与布局，不把这些展示状态加入 MCP。
- 不重写已交付的队列查询、清空或迁移，不新增数据库字段，不撤销 Codex 实际队列，不自动重发或重启会话。
- 不启动其他会话、不执行 Git 暂存或提交、不安装插件、不操作真实数据库或开发服务器；按已接受计划修改产品源码并使用临时测试数据库。

## Scenarios / 场景

- Agent 或 CLI 使用者按房间、话题或相关成员查询当前有效积压，按最新在前向更早消息分页，不依赖聊天当前页。
- 用户要求清空指定范围时，通过同一业务 API 清空全部未完成记录，包括未加载分页；结果准确说明影响的消息数。
- 查询某成员相关消息时，返回其发送或作为实际接收人的消息；与话题条件组合时取交集，并可进行现有的字面关键词查询。
- 查阅历史投递时仍能看到原状态、时间和内部删除标记，不把历史 queued 记录误判为当前有效积压。
- Agent 收到积压消息时，能用消息 ID 查询原文，用序号按需查询后续背景，判断同一事项是否已被后续明确决定覆盖。
- 两个会话没有交叉文件、接口依赖、阻塞或需对方处理的事项时，各自在本会话工作；有交叉影响时再共享必要信息和验证证据。

## Acceptance criteria / 验收标准

- A01：新增 `queue_list` MCP 工具及 `agent-relay queue list ROOM`，通过共用客户端访问现有 GET `/api/room/{id}/queue`。支持可选 `topic_id/member_id/before_seq/limit`，结果沿用 `messages/totalMessages/hasMore/nextBeforeSeq`；仅纳入未删除且存在 pending/submitting/queued 投递的消息，seq 降序、严格向更早消息分页。
- A02：新增 `queue_clear` MCP 工具及 `agent-relay queue clear ROOM`，访问现有 DELETE `/api/room/{id}/queue`，支持可选话题与成员范围，返回 `removedMessages`。操作覆盖该范围全部分页，只标记未完成投递，保留原消息、已接收记录、原状态、时间与回执，不调用 Codex 队列或会话操作。
- A03：明确范围属于消息范围：成员命中发送者或发布时保存的实际接收人，话题与成员条件取交集。按成员清空会处理这些相关消息的全部未完成 Agent 投递，不声称只清理该成员的收件投递。
- A04：`room_get/message_list` 的 MCP、客户端与 CLI 说明改为相关成员筛选，并补齐 HTTP 已有的 `keyword` 参数；保留既有参数位置与默认行为。`member_context` 继续遵循自身可见范围，不以房间查询筛选替代它。
- A05：新队列工具及受影响的消息查询 Schema 表达 HTTP 已有的参数约束；成功继续使用 `{requestId, data}`，失败继续使用现有错误和未知结果契约。清空工具明确为破坏性写入，未知结果不自动重试；成员上下文的位置写入和会话观察工具既有注解不退化。
- A06：历史投递查询保留既有返回范围和 `deletedAt` 原始事实，说明 `status=queued` 不等于有效队列；不增加 deleted、已发布或任务完成等状态，不因队列为空推断全部接收成功。
- A07：实际投递头部除原有房间、发送者身份与正文外增加来自保存消息的 `messageId/seq/createdAt`，发送者字段统一为 `sender: <sender_name>（<sender_id>）`。与上下文查询返回的 ID、房间内序号和发布时间一致；不改 clientMessageId、原接收核验、回执关联和重发策略，不重写已入队历史消息。
- A08：Skill 明确仅在交叉影响、依赖、阻塞或需要对方行动时沟通，不要求独立任务持续向频道汇报；有延迟或冲突迹象时按需查询相关背景，区分需求补充与明确覆盖，不机械以最后一条消息替换整个目标。交接包含改动范围、实际检查、未验证项和证据有效版本。
- A09：Skill 明确 queued/received 均不代表任务完成；业务清空不保证撤回外部已入队消息；全部筛选表示查询不限定、不是广播目标；订阅更新是全量替换，省略 topic_ids 会清空订阅。保留显式发布、未知发布找回、引用不继承目标及无需层层确认等既有规则。
- A10：更新唯一 Skill 源码、MCP 说明和必要 README 使用说明。相关客户端、CLI、MCP 与投递检查通过，记录准确命令、结果和未运行项；不将插件安装或真实会话操作作为单元/适配器检查前提。

## Workload and decomposition / 工作量与拆分

中等规模。主要结果是将已有业务契约完整接入 Agent 使用入口，并完善消息定位与协作指导。涉及共用客户端、CLI、MCP、投递文本、Skill 和既有测试；现有业务 API 可直接复用，没有待调查的新协议或数据迁移。

不拆分独立 task。适配器依赖同一客户端，Skill 需要消费最终工具契约，由用户安排一个接手会话串行实施和自检，可减少共享修改与交接成本。接收、进展和交付统一写入父级计划，整体验证写入同标识验证文档。

## Questions and decisions / 问题与决策

- 本任务的 Skill 指 `plugins/agent-relay/skills/agent-relay/SKILL.md`；不涉及商品或计费 SKU。
- 清空沿用当前消息范围语义，不另增只针对某接收人投递的清空接口；该差异必须在工具与 Skill 中解释。
- 历史投递查询保留兼容行为，不新增 `include_deleted` 参数；当前有效积压使用独立队列查询。
- 新增定位字段用于查阅和引用；序号或时间本身不能证明某条业务指令已失效，仍需识别同一事项的明确后续决定。
- 用户明确发送者头部使用 `sender:`，替代当前生产文本中的 `发送者:`；姓名与成员 ID 格式保留。
- 无未决意图问题。详细实施安排见同标识计划；其初始 Draft 状态已在本任务接收时复核并接受。

## Risks / assumptions / 风险 / 假设

- 业务清空不会撤回 Codex 已有队列；延迟消息仍可能到达，不能在工具文案中承诺外部取消。
- 成员范围清空可能同时影响同一消息发给其他成员的未完成投递，必须准确说明消息范围。
- 既有投递测试包含完整文本断言，头部扩展时应按真实保存消息更新断言，避免仅放宽匹配而漏掉错误 ID 或时间。
- 插件安装缓存不会因仓库 Skill 修改自动刷新；后续交付应说明使用既有安装流程加载新版本，但本任务不默认操作用户安装环境。
