## 结论

当前结构已满足本轮要求：`content` 中的标记保留顺序、重复出现和准确位置，`capabilities` 保存去重后的身份；API、数据库及草稿沿用两者。新增回归用例核对多行、emoji、重复标记与引用消息一起保存和恢复，未修改生产代码或依赖。

剩余差距是编辑框显示和交互，属于后续第二步。届时可评估独立的 `SkillMessageEditor.vue`，使用 CodeMirror 6 保留当前 Markdown 源文编辑模型，通过替换装饰把正文中的 Skill 引用标记显示为不可拆分的行内标签；最终仍输出相同的 `content + capabilities`。光标、选区、删除、撤销、复制粘贴和中文输入需要一并验证。

评估核对了仓库源码、CodeMirror/Tiptap 官方文档及 npm 包元数据。第一步实现格式编解码、消息 Markdown 渲染与后端校验/投递转换，使用现有 Node 和 Python 工具验证；未安装编辑器依赖或进行浏览器/WebView 验证。第二步实际中文输入和标签边界行为仍需编辑器原型确认。

## 后续参考：编辑器方案比较

| 方案                                   | 与当前模型的适配                                                | 主要额外工作                                                     | 评价                                            |
| -------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- | ----------------------------------------------- |
| CodeMirror 6 的替换装饰与 atomicRanges | 文档仍是字符串，可以保留 Markdown、换行、引用标记和现有消息字段 | Vue 封装、标签装饰、候选查询、剪贴板与发送快捷键；标签边界需验证 | 推荐；官方已有“占位文本显示为整体 widget”的示例 |
| Tiptap/ProseMirror 的行内 Skill 节点   | Vue 集成及 mention 节点成熟，但引入结构化编辑文档               | 节点与现有 Markdown 字符串之间的转换、换行和格式保真             | 可行；将来扩展完整富文本时更适合再次比较        |
| 自行实现 contenteditable               | 可直接绘制标签，新增依赖少                                      | 手工维护 DOM/模型映射、选区、输入法、粘贴、撤销和浏览器差异      | 隐性维护成本较高，不建议作为本次主方案          |

CodeMirror 的装饰负责显示，atomicRanges 负责让常规光标移动和删除把引用范围视为整体；程序化修改、输入法、拖选及剪贴板仍需接入约束。引入成熟内核可以减少基础编辑状态维护，并不代表接入后自动满足全部验收条件。

依赖应按需选择 state、view、commands 及必要的 Markdown 支持。最终包体增量应通过实际生产构建测量，本轮不把 npm 解包大小当作发布包体。

## 正文格式与引用契约

继续使用两个字段：content 负责正文顺序，capabilities 负责引用身份及实际加载。第一步采用如下格式，名称中的反斜杠和方括号使用 Markdown 转义：

```json
{
  "content": "请先用 [dev-check](skill:skill-xxx) 检查，再修复问题。",
  "capabilities": [
    { "type": "skill", "id": "skill-xxx", "name": "best-practices:dev-check" }
  ]
}
```

- 选中 Skill 时，在同一个编辑事务中替换当前 `$查询词`，光标移到标签之后；正文继续按 Markdown 源文编辑。
- 以 ID 绑定已选择的引用，显示名称来自 capabilities 的名称快照，不依赖 `$名称` 猜测身份，也不把本地路径写入正文。
- 同一个 Skill 可在正文中出现多次；新消息的 Skill 引用列表由有效行内标记汇总去重，移除最后一次出现时才移除对应引用。撤销/重做也必须同步。
- Markdown 的代码块、行内代码和转义示例保持为文本；编辑器与历史展示采用相同的识别约定。自定义 skill 链接需专门解析，不能假设 markdown-it 默认支持该协议。
- 后端检查识别出的引用标记是否对应 capabilities 中的 Skill。标记不携带任何可执行路径；实际可用性继续由投递 adapter 按目标会话检查。
- 新消息的行内标签不再在正文上方重复展示。历史数据保持现状，不扫描、不回填、不迁移。
- 空正文判断需要排除 Skill 标记，保留当前“仅选择 Skill、没有正文时不能发送”的行为。6000 字符限制需与现有接口一致，插入后的序列化长度也要校验。
- 可读文本转换用于复制正文、回复预览、队列摘要和 Codex 投递，输出可辨识的 Skill 名称；发布重放及待确认请求仍比较和恢复原始序列化正文。

## 后续参考：完整编辑器的验证重点

- `$` 选择后标签在光标位置，标签前后文字和换行保留；连续选择和同一 Skill 多次出现均正确。
- 左右移动、鼠标拖选、Backspace/Delete、跨标签选区删除将标签作为整体处理；撤销重做同时恢复正文和引用身份。
- 中文输入法确认不会发送消息，候选框打开时 Enter 只选择 Skill；普通 Enter 发送，Shift+Enter 换行。
- 编辑区内复制粘贴保留引用身份；粘贴普通外部文本不凭名称自动加载 Skill，粘贴引用时按当前房间核对身份。
- 同一房间普通模型同步不重置有效选区，不通过整段重建文档更新 Vue；切换房间和待确认恢复时，不把旧编辑器内容写回新房间或改写冻结请求。
- 新消息发送、重新加载后标签仍在原位；复制、引用及队列摘要为可读文字；代码中的 Skill 示例不被转换。
- 引用标记与列表不一致时有确定的校验结果；仅有标签时仍按空正文处理；原生 Skill 加载及未知结果不自动重发的规则保留。

界面由用户自行测试。实施阶段应给出明确的人工步骤，不能用 Node 单测或源码检查代替输入法、DOM 和剪贴板证据。
