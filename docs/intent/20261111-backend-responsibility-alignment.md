## Goals / 目标

- 沿完整业务链路审视 application、domain、infrastructure，形成业务规则、用例、存储原子操作、查询投影、协议适配和运行机制的职责清单，逐项说明保留、迁移、合并或删除的理由。
- 让每类业务决策与完整用例有明确归属，成员生命周期、消息发布、上下文提供和投递动作不再依靠跨多个不相关文件追踪才能识别主流程。
- 领域层承载稳定业务语义和可独立验证的约束；应用层组织操作顺序和一致性要求；基础设施层实现持久化、协议和执行机制，并保留必要的条件更新与竞争保护。
- 明确 Repository、Query/Reader、Store、Service、事务能力及 DTO 的语义，保留有实际用途的抽象，收敛重复端口和无独立责任的转发层。
- 保持当前业务行为、公开接口、持久事实、并发约束、事务与资源生命周期，使用有针对性的规则、用例和集成证据验证调整结果。

## Non-goals / 非目标

- 不增加产品功能、权限体系或新的投递承诺，不修改当前 HTTP/CLI/MCP/WebSocket 契约与既有数据库结构；如审视发现确有必要改变，先记录范围与影响。
- 不更换 FastAPI、同步 SQLAlchemy、SQLite 或 Codex 接入方式，不引入异步数据库栈、微服务、事件溯源、完整 CQRS 框架、通用 DI 容器或工作流引擎。
- 不按表建立 Service，不按目录建立独立领域或每模块 UoW，不为了形式纯粹机械复制 DTO、移除所有 Pydantic 模型或将所有 SQL 判断搬到 Python。
- 不将简单只读查询全部包装成转发 Service，不将原子领取、身份条件写入和位置单调更新拆成无保护的先读后写。
- interfaces 与 bootstrap 作为三层职责的连接边界参加核对和必要接线，不扩大为协议、配置、日志或前端的全面重写。
- 不执行 Git 写入、真实数据库操作或服务启停；开发检查不等同于整体 Verification，独立 web 工作不纳入本任务。

## User stories / scenarios / 用户故事 / 场景

- 开发者调整成员加入、编辑、退出或状态观测规则时，能找到所属应用能力与领域规则，并区分会话协议转换和数据库条件写入。
- 调整消息接收人、发布幂等或队列有效状态时，有明确的业务语义来源；仓储继续原子保存消息、投递和事件，并保护并发序号及身份。
- 提供成员上下文时，应用代码能表达读取、授权范围、提供记账和位置推进的完整流程；查询适配器仍在数据库侧筛选与分页，实际结果及记录保持共同提交。
- 调整投递状态或未知结果处理时，能分辨领域状态规则、应用动作、Codex 原始协议校验和 runner 的执行机制，避免重复外部提交或错误重试。
- 读取房间列表、快照、消息页和统计时，Query/Reader 可以直接形成所需视图，不为读取强制恢复完整聚合或增加无业务价值的中转。
- 调整某条业务链路后，可分别验证规则与用例、SQL 并发保护和协议边界，且多个仓储仍可共享同一用例事务，外部等待不占用数据库作用域。

## Acceptance criteria / 验收标准

- A01：审视覆盖三层及其连接边界；R01—R08 均有事实、处理结论、最终责任位置和证据，明确哪些现有实现应保留，不能只交付应用层拆类或目录移动。
- A02：领域层的业务状态、约束、默认值和策略有明确来源；规则可使用业务值直接验证，不依赖数据库、网络、框架请求或装配。Pydantic、序列化和协议事实类型按实际语义决定复用与拆分，避免重复或无效抽象。
- A03：资源/成员、消息、上下文提供和投递有连贯的用例归属。应用表达操作顺序、外部调用及一致性要求，不接触 Session、ORM、SQL 表达式、原始 RPC 响应或具体基础设施。
- A04：Repository 保留明确的存储原子能力，包含必要的领取、条件更新、身份核对及位置单调更新；业务策略与 SQL 实现分工可核对，不因提取规则破坏并发保护，也不将完整用例隐藏在持久化命名之下。
- A05：区分纯读取投影与带记账副作用的上下文提供；简单 Query 不强制经过转发 Service。可见性筛选在分页前由数据库执行，提供结果、提供记录、位置和事件同事务；保留当前独立可见性规则。
- A06：Codex 适配器负责协议交互、原始数据校验和边界转换，应用负责投递/接收事实及失败语义，runner 负责执行机制。未知结果不自动重发，首项启动、原输入身份、跨房间会话互斥和清空竞争保护不退化。
- A07：同一请求或用例内的仓储可共享统一事务机制，不增加每模块 UoW 或分割提交；请求响应前提交、异常回滚、RPC 与 WebSocket 等待前释放、并发 Session 隔离和资源所有权保持。
- A08：以当前提交为保持基线，保留固定用户与 Agent 的区别、房间改名、当前 Topic 字段、软删除、订阅/路由、发布幂等、字面搜索、分页及事件补取；保持数据库结构、时间/回执编码和各公开接入方式，不回退已提交的独立行为。
- A09：实施时沿真实职责调整规则/用例测试和必要集成测试，保留有意义的现有断言；使用项目既有 pytest、mypy、Ruff 入口，按实际授权和修改范围记录执行与未执行项。既有 474 项通过属于前一重构证据，不能自动证明未来调整通过；本次记录不重跑检查。
- A10：最终架构说明与实际调用链一致，能够从一条业务规则定位决策者、用例入口和基础设施实现；新增、保留、合并或删除的抽象均说明必要性，整体 Verification 核对最终集成快照。

## Workload assessment / 工作量评估

- 主要交付：三层职责清单及目标契约、按业务链路调整的实现与测试、正式接线与架构说明、可追溯的开发检查结果；整体验证另行进行。
- 工作量：中等偏大。相较 SQLAlchemy 替换，本次涉及业务归属、类型和端口、查询与复合写入、驱动与后台机制的共同演进，不能仅通过 Service 拆分完成。
- 复杂度：较高。最困难的是区分业务决策和原子持久化，在减少概念的同时保持事实、作用域与并发行为；源码中已有有效规则和抽象，应逐项判断而非全面重写。
- 风险：较高。上下文记录与位置、发布与固定投递、队列状态竞争、外部未知结果和资源所有权跨层关联，形式上更整齐的代码也可能破坏行为。
- 关键未知项：领域状态及事件对象的最小有效形态，资源与成员的职责切分，Store/Repository/Reader 的最终契约，以及回执、历史游标和调度策略的责任归属。需在 Plan 或明确的调查节点中形成结论，不能假定上一轮建议的目录就是最终方案。
- Review 上下文：当前架构说明、上一轮 SQLAlchemy 计划与验证限制、三层源码、HTTP/后台装配，以及现有规则、成员、消息、上下文、投递、事务和生命周期测试。
- 耦合与共享修改：`RoomState`、业务模型/契约、RoomStore、消息读取、事件与公共夹具均由多条链路使用。先统一契约与约束，再按依赖调整业务链路；每个节点同时处理涉及的三层和对应测试，不将三层分配为互不协调的三个重写任务。
- 结论：以可审查的业务链路拆分 task；正式粒度、执行 DAG、写入范围和版本条件以总计划与执行记录为准。

## Decisions / 决策

- 用户明确审视 application、domain、infrastructure，持久化之外的 Codex 协议适配与后台运行机制也纳入基础设施责任核对。
- 以实际业务流程和决策归属作为判断依据，继续采用现有分层基础；按能力组织的目录是可选方案，不作为本意图已接受的具体结构。
- 规则可以使用函数、dataclass、枚举或适当 Pydantic 值；Repository 可提供原子业务存储能力，Query 可直接生成投影。是否拆分取决于责任和变化原因。
- 保留统一事务机制、必要的 SQL 筛选及条件更新；应用组织流程，仓储完成持久化，事务所有者负责提交与回滚。
- 新任务独立记录，不将历史阶段授权、测试结果、数据库或服务操作授权自动转移到本任务。

## Risks / assumptions / 风险 / 假设

- 假设本次调整维持当前业务承诺和数据库结构，审视发现的业务缺陷与架构问题需区分登记；需要行为变更时先明确验收差异。
- 领域规则与数据库条件可能表达同一业务约束的不同部分，不能为了追求单一实现而删除数据库最终保护，也不能只把常量搬进 domain 就声称职责已完成治理。
- 为抽象补齐空层、复制 DTO、引入通用基类或强行包装所有查询会增加理解成本，需在每个节点审查中说明抽象价值。
- 现有后台服务包含共享游标等运行状态；重新组织时需核对所有者、并发访问和退出语义，不在本意图提前判定必须迁移。
- 独立 web 工作仍在推进；实施和验证前需重新核对实际提交与依赖，保留无关修改，不将当前意图范围扩大为前端清理。
- 初步调查只有静态证据；各任务实施后的定向和完整开发检查见执行记录，整体 Verification 仍需按对应阶段开展。
