## Background and goals / 背景与目标

- 用户观察到：目标工作者忙碌时，消息很快入队，却长时间显示“接收中”，消息持续堆积。
- 用户的目标是提高消息时效，明确“已有实现都可以改”；发送消息时不增加排队、插话等模式选择。
- 当前实现统一使用 Codex `thread/queue/add`，忙碌时输入通常等待当前轮次结束；入队回执与会话收到输入是不同事实。后台提交还可能占满执行槽位，使接收核验迟迟得不到调度，这是源码中的另一个风险，尚未证明是用户现场的原因。
- 对新消息自动选择更及时的输入路径：目标有正在执行的轮次时补入该轮次；空闲时沿用队列及原有受控启动。页面和 CLI/MCP 发布入口使用同一规则。
- 保留消息正文、路由、能力引用、原会话绑定和防重复约束。状态必须说明实际进度，不能把提交成功显示成工作者已读、已处理或已回复。

## Non-goals / 非目标

- 不暂存或创建 Git 提交，不部署或操作真实用户会话；产品实施已由后续“开始实现”授权。
- 不增加投递模式开关，不中断工作者、不代答审批、不接管原 Codex 执行宿主。
- 不将已进入 Codex 队列的历史消息再次补入当前轮次，不迁移或重放现场积压。历史积压继续按原队列消费。
- 不承诺正在运行的工具立即停止，也不承诺模型在固定秒数内读完、处理或回复消息。
- 不借本功能增加消息优先级、合并丢弃、无限重试、事件常驻连接或独立监控系统。

## Scenarios / 场景

- 工作者正在处理长任务：新消息进入当前轮次的输入通道，不再固定等待下一轮才提交。
- 工作者空闲：新消息进入原队列，只对新成功提交触发原有一次性队首启动。
- 读取忙碌状态后轮次恰好结束：仅在确定未接纳且满足计划中的竞态条件时退回队列，不能双投。
- 提交后连接断开或响应超时：保留“结果待确认”，继续核验同一个客户端消息标识，不自动重发。
- 含 Skill/MCP 引用、多目标发送：每个目标分别验证能力和投递；单个目标失败不影响其他目标。
- 持续发布消息：接收核验仍能获得执行机会，已经进入会话的输入可以及时更新状态。
- 清空待办记录：不能宣称撤回已经送入工作者当前轮次的内容。

## Acceptance criteria / 验收标准

- A01：忙碌目标的新投递自动使用当前轮次输入，不调用新的 `turn/start`，不要求用户选择投递模式；空闲目标沿用原队列与单次、精确队首启动。
- A02：轮次竞态、版本不支持、明确拒绝、响应损坏和连接结果未知均按计划分类；任何可能已接纳的输入不再自动发送第二次。恢复、观察和清空不能触发重发。
- A03：两条路径均保存原 `client_message_id`；只有历史 `userMessage.clientId` 精确匹配后才标记 `received`。接纳回执、历史接收、处理和回复含义明确。
- A04：原目标会话、项目目录、消息 envelope、必需 Relay Skill、所选 Skill/MCP 原生输入及逐目标能力校验保持完整；能力确定无效时外部输入写入次数为零。
- A05：持续提交时接收观察不会无限饥饿；有界并发、同一会话不并发提交、历史分页和未知结果只核验不重放保持。单并发配置也不会让观察反过来饿死提交。
- A06：旧消息、旧回执和已入队积压不重投；新增投递事实采用兼容的前滚迁移。队列删除仍只作用于真实队列项，不把当前轮次 ID 充作队列 ID。
- A07：页面用“发送中 / 接收中 / 已接收”以及“发送失败 / 发送待确认”表达进度；不加入模式选择，清空不暗示撤回已送入会话的输入。发布请求和状态筛选保持兼容。
- A08：提供有意义的单层单测、静态检查和离线迁移 SQL 证据；不恢复已删除的测试支持目录。Implementation 不新增或运行真实 SQLite、跨层集成、浏览器或界面测试；用户后续授权整体 Verification，可使用 jev-ultrafast-mcp 在隔离运行环境和独立测试会话中自测界面与投递链路，不操作原用户数据库或工作会话。

## Questions and decisions / 问题与决策

- 已确认目标：用户说“从用户视角来看，我就想提高消息的时效性，已有实现都可以改”，采用自动路由，不增加用户选择。
- 阶段授权：用户先要求分析、记录与拆分，随后明确“开始实现”；已按计划完成实施及必要开发检查，未扩大到 Git 写操作或真实会话操作。
- 接入选择：`turn/steer` 是向 Codex 活动轮次追加用户输入的 app-server RPC；本项目沿用现有 CLI proxy 连接共享 daemon 发起 RPC，不另起执行宿主，也不以模拟终端按键实现。
- 当前协议依据为本机 `codex-cli 0.167.1` schema。它包含官方页面示例未展示的可选 `clientUserMessageId`，因此沿用现有精确历史核验，不把 steer 成功响应直接当作已接收。
- 无待用户回答的产品范围问题；技术方案供审查，见总计划。

## Risks / assumptions / 风险 / 假设

- steer 提高输入进入活动轮次的时效；工具长时间运行、审批等待或模型处理仍可能带来延迟。
- 新消息可能比历史队列积压先被当前轮次看到；本功能有意改变跨轮次的到达顺序，不改变 Relay 消息序号或同一目标的新消息提交顺序。
- 已完成源码、schema、单层单测和构建检查；随后在独立测试会话确认忙碌消息进入原轮次、保留客户端 ID。实测历史确认仍有数秒至数十秒延迟，不据此承诺固定端到端时延。
- 老版本或活动轮次不可定位时允许按总计划回退队列，并记录原因；不能悄悄丢失消息或能力引用。
