## Background / 背景

用户在 `room-a2493e542ba3/channel-de13b3967e24` 的 `msg-0289` 明确：用户和 agent 只负责发布，路由及投递由业务实现负责，可以接受延迟，不能因内部加锁冲突就结束为失败。`msg-0290` 指定架构师统筹、其他成员协助；`msg-0299` 要求用 SpecFlow 记录，并明确请求事务足以控制消息入库、必要协调应以频道为粒度、使用后台任务和小事务异步投递。

已核对的事实：消息及接收人投递记录已经同事务保存；后台 DeliveryRunner 已存在。当前投递与启动路径持房间文件锁跨越 RPC，获取失败被归为 unknown。原房间 7 次故障均在 operation 入口、driver 调用前发生，日志位置为 `logs/conflua.log:9126`、9149、9281、9327、9344、9448、9483；协助证据见 `msg-0296`、`msg-0297`，汇总结论见 `msg-0298`。

驱动还将部分输入提交前的断连／超时归为 rejected。仓库隔离实验 [去重证据](../design/evidence/20261107-codex-0.167.0.json) 显示 Codex 0.167.0 相同 clientUserMessageId 的两次 add 未去重，不能把自动重发用于推断不明结果；该实验不是当前版本的新实测。

## Goals / 目标

- 已受理的消息及各目标任务持久保存，后台持续推进；内部竞争转化为等待，发送方不负责补发。
- 请求事务负责消息及路由结果的原子入库，外部提交放到事务提交后的后台执行。
- 投递采用小事务领取、事务外 RPC、小事务保存结果；有必要的业务互斥以频道为边界。
- 按目标 session 有序调度，暂时故障自动退避恢复，其他可调度目标继续推进；回执与真实接收各有证据。

## Non-goals / 非目标

- 不将清空、归档或撤回功能重设计纳入本问题。
- 不调整生产队列并发配置掩盖问题，不自动补投历史记录，不管理服务或 Git 提交。
- 不开展 UI 测试、真实成员会话投递实验或并发压测；不承诺未经上游支持的恰好一次消费。

## User stories / scenarios / 用户故事 / 场景

- 用户或 agent 发布一条消息给多个接收人，业务保存路由后逐个推进，不因属于同房间而部分永久失投。
- 某一目标正在提交或等待退避，后续同目标任务有序等待；其他频道或目标利用可用容量继续执行。
- 输入写入前临时断连，后台稍后重试原任务；已得到回执但本地写库失败，只重试保存结果。
- RPC 结果不明时业务核验原队列及输入历史，界面状态忠实表达证据，不将未找到当成可以重发。

## Acceptance criteria / 验收标准

- A01：消息、发布幂等标识、路由接收人和投递任务由现有请求事务原子保存；消息入库不增加文件锁。
- A02：只有已提交任务可被后台领取；发布不等待 Codex RPC，受理成功后的正常竞争不要求发送方重发。
- A03：领取和结果保存各自使用短事务，提交／启动 RPC 期间无数据库写事务或房间级业务长锁；确有业务协调必要时使用 roomId/channelId 边界并写明用途。
- A04：同目标 session 按持久化投递顺序串行提交，提交与必要启动处理的占用不会过早释放；队首退避时后项不越过，顺序不使用跨房间 seq 比较。
- A05：同频道多接收人及其他频道／房间在并发容量内正常推进；一个目标忙碌不会使其他任务因房间锁直接进入 unknown/rejected。
- A06：明确未写入外部输入的暂时故障可退避重领，原任务及关联标识不变，重试时间持久化且重启后可继续；确定配置／绑定错误和暂时故障分类准确。
- A07：已取得外部回执后的本地保存失败只重试保存，不再次发输入；条件更新保留现有状态约束，不将普通处理异常无差别归为发送未知。
- A08：真实发送不确定按原标识持续核验；精确队列命中证明入队，完整输入历史证明接收，未命中或不可读不证明未发送；无幂等保证时不盲目重发。本轮新尝试产生的有效 unknown 保持同目标后项顺序屏障，取得正向事实后放行；迁移前历史 unknown 保持原有处理，不因此新增阻塞或补投。
- A09：使用既有后端检查及确定性单测验证调度、退避和回执边界，记录实际版本与未运行项；不以入队回执冒充 received，不依赖真实 Codex 或 UI 测试。

## Workload assessment / 工作量评估

工作量中等，主要交付为调度及事务边界、恢复状态和回执处理、确定性回归证据。复杂度中等偏高，涉及 driver 真实输入写入边界、同 session 串行与频道范围、重试状态持久化及版本迁移。风险集中在误分类导致永久失投、提前释放占用、同目标重试越序及重复发送。

结论：建立三个串行 task。调度机制、恢复机制和回归证据可以独立审查；共享 delivery service/store/repository 及测试契约，实施串行整合，避免多人同时修改相同文件。已有暂停试改不作为已接受方案或交付，开工前核对实际工作区。

## Decisions / 决策

- 请求事务入库，无附加入库锁；后台任务和小事务异步投递。
- 必要业务协调采用频道粒度，目标串行通过调度表达，不再依赖房间文件锁包围 RPC。
- 已知未发送与可能已发送分开处理，准确保留入队／接收证据；复用现有持久化、后台执行器和检查工具。

## Risks / assumptions / 风险 / 假设

- 上游接口、版本及错误码缺乏某些明确承诺，分类须依据具体阶段与证据，不能将所有前置错误当成暂时故障。
- 只在内存中退避不足以保证重启恢复；若增加字段，需同步模型、迁移及打包资源，不对运行数据库直接试改。
