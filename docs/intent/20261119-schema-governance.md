## 背景与目标

- 当前自有资源 ID 混用带前缀的随机字符串、房间 ID 加消息序号、消息与成员拼接值和 UUID；审计列覆盖不一致，部分软删只靠时间字段表达。统一 Schema 约束，同时保持频道隔离、消息顺序和投递行为。
- 自有实体使用 [tsid-python](https://github.com/luismedel/tsid-python) 的规范字符串：无前缀、13 位大写 Crockford Base32。SQLite 存 `TEXT`，接口传字符串。开发旧库允许离线重新分配 ID 并完整改写引用。
- 所有业务表具备 `created_at`、`updated_at`；创建时间由数据库 INSERT 默认值保证，修改时间可空，实际更新时赋值。已有软删语义的表显式保存删除状态与时间。
- 数据库时间统一存 UTC。浏览器和 CLI 已有的面向人时间展示使用所在设备的本地时区；结构化输出保持 UTC，不为此新增展示入口。
- 就地更新 SQL-first 建库定义、种子和 ORM。新版本不自动升级旧库，为开发库提供一次性离线 Python/SQL 转换；失败不破坏原库或图片。

## 非目标

- 不做双读双写、旧 ID 别名、旧 URL 重定向、版本混跑或发布版自动升级；已发往外部系统的旧链接、旧浏览器草稿不保证继续可用。
- 不重写 Codex 会话和投递回执，不将业务序号、事件游标、外部标识或关联表自然键改成 TSID；不扩大软删范围，不重新设计投递或 Git worktree 生命周期。

## 场景与验收

| ID | 场景及可检查结果 |
| --- | --- |
| A01 | 安装和启动：空库从新基线建成，种子、SQL、ORM 与主外键一致；旧 revision 不被运行时或常规迁移入口自动改写，并能看到离线处理指引。 |
| A02 | 创建和更新：全部业务表（含关联表、追加式事件表）有 UTC `created_at` 与可空 `updated_at`；省略创建时间仍能写入，业务更新、批量更新、upsert 和软删正确刷新 `updated_at`，不覆盖创建时间。 |
| A03 | 删除和归档：房间、频道、话题、成员、消息、投递的删除状态与时间一致；重复删除保留首次时间；频道归档仍可读且保留历史，业务投递状态不被删除覆盖，作用域内活动唯一约束和原有级联行为保持。 |
| A04 | 资源识别：自有实体及种子生成规范 TSID；默认频道和固定人类成员按业务属性识别，保留每房间/频道的唯一性及频道隔离；消息分页、事件游标和队列顺序不依赖 TSID 时间。 |
| A05 | 客户端行为：Web、CLI、MCP 使用真实资源 ID，频道创建结果未知时沿用已知 ID 查询、不重复创建；默认频道导航、固定用户显示、图片上传和读取无回归。现有界面时间及 CLI 文本时间（如有）按本地时区显示，JSON 保持 UTC。 |
| A06 | 开发旧库保留：脚本在停机副本上按原作用域重分配 ID，旧源不变；行数、外键与结构化引用守恒，历史时刻（统一为 UTC）、归档/删除、消息与事件顺序、Codex 标识和回执保留；历史受管图片可读，既有 worktree 不搬动。明确失败退出、校验报告、切换和恢复步骤。 |

## 工作量与候选拆分

工作量中高：涉及 16 张业务表、仓储写路径、资源生成与默认身份定位、客户端和离线资产转换。复杂度主要来自复合作用域、历史事件多态引用、依赖 `rowid` 的稳定顺序，以及 SQLite 和图片分开存储。风险最高的是迁移误标归档、图片或外部回执断链、旧库被启动流程误写。

| 候选任务 | 输入与依赖理由 | 单一交付与验收归属 |

拆分依据：持久化契约须先固定；服务端完成后，客户端和离线脚本的文件可分开修改。主会话在一份集成基线上复核实际差异和证据；局部验收不代替整体验证。

## 待定问题、决策与风险

- 用户已确认 TSID 字符串、开发库可离线批量重分配 ID、不承诺自动升级。暂无需用户提前决定的意图问题。
- 规划假设：离线脚本初版只接收当前 `member_roles_20261118` 源 revision；不认识的库拒绝，不猜字段结构。更早库不是本次离线脚本的交付范围。
- 规划约束：迁移生成的 TSID 不是真实历史创建时间；对缺少可信创建时间的记录使用统一迁移基准时间并报告，不改已知时间。TSID 不取代 `seq`、`event_id` 或投递顺序。
- 需在实施方案里复核发号部署约束和离线演练证据；服务端实现前不声称不同进程节点已经协调，也不假设实际开发库无坏数据。
