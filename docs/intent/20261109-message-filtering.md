# 意图：统一话题与成员消息筛选
最后修改时间: 2026-11-09 16:55:31

## 审查状态

Accepted

## 背景与目标

话题查询和前端实时追加目前会额外包含发给固定用户“你”的消息，使无话题消息出现在任意话题中。成员筛选目前只匹配发送者。用户要求严格匹配所选话题，并补充成员筛选同时包含该成员发送和接收的消息。

## 规则与场景

- 全部消息：清除话题和成员条件，显示房间所有消息。
- 话题 T：仅匹配 `topicIds` 包含 T 的消息；跨话题消息可分别匹配，无话题消息不匹配任何话题。
- 成员 M：匹配 `senderId = M` 或 `recipientIds` 包含 M 的消息，固定用户遵守同一规则。
- 话题 T 与成员 M 同时选中：取两项条件的交集。
- 接收者使用发布时解析并保存的 `recipientIds`，包括由话题订阅产生的接收者；不按当前订阅、单独的 @ 字段或投递成功状态推断。
- 同一维度单选；切换话题保留成员条件，再次点击已选成员取消成员条件。没有匹配消息时显示空结果。
- 首次加载、历史分页、是否还有更新消息和实时追加使用相同谓词，按 ID 匹配，改名不改变结果。
- 用户点选侧栏话题或成员时，发送区两组 checkbox 同步当前筛选；点击全部消息清空两组勾选，保留正文。发送区仍可手动调整多个话题或成员，不反向修改筛选。选择固定用户“你”不产生给自己的 @；待确认的已发布请求保持原始路由。

## 非目标

不改变发布路由、Agent 上下文可见范围、投递队列、数据库 schema、全房间统计及发送或引用跳转的导航行为；不扩展 README。

## 验收标准

- A01：所选话题不混入无话题、其他话题或仅发给“你”的消息。
- A02：成员筛选涵盖发送者、直接接收者、经话题解析的接收者；无关成员不匹配，每条消息只出现一次。
- A03：组合筛选取交集；“全部消息”、切换话题和取消成员选择维持上述语义。
- A04：首次加载、历史分页和实时追加结果一致，分页游标及 `hasMore`、`hasNewer` 只依据匹配消息计算；已有消息投递状态更新继续生效。
- A05：点选、切换或取消侧栏话题/成员，同步发送区勾选；全部消息清空勾选但保留正文，之后手动修改的路由按当前勾选发布。

## 工作量与拆分评估

主要交付是一个跨后端查询与前端状态合并的统一筛选契约。工作量小，复杂度低；风险集中于分页条件及实时追加漏改。必要检查覆盖 API、查询分页、Pinia 合并和页面选择交互。已有 ID 与收件人数据足够，无需调查 schema。后端与前端修改需共同交付，保持单任务，不创建 task。

## 待定问题与风险

暂无需要用户确认的未决事项。工作区已有成员改名、时间线布局、成员弹窗等修改，本任务只叠加筛选变更，保留其他工作。
