## 场景

- 发布消息时，应用用例完成发布身份、幂等、引用和目标的业务检查，使用独立规则计算实际接收人，并通过存储能力原子保存消息与固定投递。用例不接收 SQL 连接或 Codex 原始协议对象。
- 添加成员时，先读取必要事实，结束短事务，再核验原会话，随后在短写事务内重新检查并保存绑定。协议适配器负责 RPC 和协议状态转换，业务层负责归属及加入条件。
- 查阅上下文时，保留当前可见范围、提供记录和位置单调推进语义，相关读取与写入保持原子。普通目录、位置及历史查询继续遵守各自的读写性质。
- 后台投递时，运行器负责锁、轮询、并发与关闭，应用动作负责一次提交或接收核验。外部调用不持有数据库事务，并发动作不共享数据库连接。
- HTTP 和 WebSocket 通过各自作用域取得已装配的能力；CLI、MCP 继续经 `RelayClient` 消费 HTTP 服务，共用服务端语义，不要求改为进程内直调应用。
- 规则与用例测试使用业务值及轻量端口实现；数据库、HTTP、外部协议和子进程测试保留明确的集成职责。

## 分层方向与抽象原则

以下为本轮讨论形成的建议，具体包名、接口方法及实施步骤在 Plan 阶段确定。

| 层 | 职责 | 约束 |
| --- | --- | --- |
| `interfaces` | HTTP、WebSocket、CLI、MCP 及执行入口的输入、身份、输出和错误适配 | FastAPI `Depends` 留在 HTTP 边界；路由不执行 SQL、不构造外部客户端 |
| `application` | 业务用例、归属校验、跨能力编排、所需端口及业务输入输出 | 不依赖具体 SQLite 存储、Codex 实现、HTTP provider 或完整部署配置 |
| `domain` | 独立规则、业务值及状态语义 | 不依赖数据库连接、网络 SDK、请求对象或装配代码；仅为实际规则建立内容 |
| `infrastructure` | SQL、事务、Codex 协议、文件锁等具体实现 | 实现消费方所需契约，将外部协议对象与异常转换到明确边界 |
| `bootstrap` | 配置加载、实现选择、对象连接、启动及关闭 | 按能力组合下层工厂，不承担业务决策或集中重建所有下层资源 |

建议采用技术层优先、层内按业务能力分组的目录布局。聊天室协作为主要业务范围，资源管理、成员查阅、会话接入与投递先作为能力划分，不按表或路由机械建立独立业务模块。

- `Protocol` 由消费方按真实需要定义，复用现有有效端口，输入输出使用中立业务类型。
- 简单查询可以由 SQL 适配器直接实现查询契约，不增加只做转发的查询服务。
- 单个存储内部的复合写入可以保留完整方法；仅当用例确需协调多个存储能力时考虑专用 UoW。
- 领域规则可使用普通函数、dataclass、枚举或适当的 Pydantic 模型，不为每层机械复制同义 DTO。
- 包级 `dependencies.py` 按能力、配置选择及生命周期归属组织；普通工厂供框架中立的执行路径使用，同作用域的少量提供器允许共享文件。
- 目录移动必须伴随实际职责和导入方向调整；不以文件数量、行数或目录层数作为治理完成标准。
