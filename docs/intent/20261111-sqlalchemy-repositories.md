## Background / 背景

- 用户要求引入 SQLAlchemy 和 Repository 模式重写数据访问层，沿用面向切面的事务管理，建立数据访问抽象，避免直接 sqlite3 依赖并减少 SQL 拼写。
- 规划基线为 `be8accd90d4ae24a8aa9b8b225d8e77f8d709e96`。工作区已有 `docs/design/codex-integration-capabilities.md` 的独立修改，不属于本任务。
- `pyproject.toml` 已声明 SQLAlchemy 2.x 与 Alembic，迁移使用 SQLAlchemy；运行时仍直接使用 sqlite3。评估时持久化目录有 7 个直接导入 sqlite3 的模块、约 81 处 execute/executemany 调用点，当前结构有 14 张业务表。
- 现有 `RoomData/RoomQueries/RoomStore`、`DeliveryStore`、`MemberContext` 已提供中立契约。应演进这些边界，拆分连接、资源写入、消息查询和后台状态写入集中在同一 Store 的职责。
- 请求事务已由中间件统一收尾；后台动作、成员绑定和 Codex 清队列已有短事务与外部 RPC 分段，重构需要保留这些行为。

## Goals / 目标

- 使用 SQLAlchemy 2.x 的类型化 ORM 映射和表达式 API 实现运行时数据访问，集中连接、Session 和数据库方言策略。
- 以业务能力定义 Repository Protocol 和查询契约，应用只处理业务值，不接触连接、Session、ORM 对象或驱动异常。
- HTTP 沿用惰性请求事务切面；后台与分段流程使用同一事务机制提供的独立短作用域，每条路径只有一个提交所有者。
- 保留现有接口、持久数据、顺序、并发保护、事件、查阅位置及未知结果处理语义，提供可核对的回归证据。

## Non-goals / 非目标

- 本轮仅创建意图、计划、task 与验证记录；不修改产品代码、不分配执行者、不启动其他会话、不执行 Git 暂存或提交。
- 首版继续使用 SQLite 和现有 `database.path` 配置，不切换数据库、不引入异步数据库访问或多数据库部署。
- 不承诺移除 SQLAlchemy 底层的 SQLite DBAPI 驱动。目标是消除产品源码对 sqlite3 API 的直接依赖，并隔离 SQLite 方言。
- 不改 HTTP/CLI/MCP 的公开契约、前端、Codex 协议、调度策略、文件锁或消息业务规则。
- 不重写历史迁移、不重建开发数据库、不回填真实数据，不操作正在运行的服务或真实 Codex 队列。
- 不建立通用 CRUD 基类、每表 Service、全局 Session、隐式 ORM 生命周期事件总线或跨系统事务框架。

## User stories / scenarios / 用户故事 / 场景

- 同一 HTTP 请求组合创建房间、更新资源并读取结果，所有写入与事件在响应开始前统一提交，任何失败共同回滚。
- 多个调用并发发布消息或绑定成员，继续获得唯一序号、发布幂等和正确冲突结果。
- 后台并行投递使用独立会话，领取、保存回执和确认输入保持原子；清空后的历史状态不会被迟到回执覆盖。
- 成员上下文查询在同一短事务内记录实际提供结果并推进位置；RPC 和 WebSocket 等待不占用事务。
- 当前迁移 head 的已有数据无需重建即可被新实现读取和更新，时间、回执、关联顺序与事件游标保持。

## Acceptance criteria / 验收标准

- A01：运行时连接、会话和 14 张表的类型映射由 SQLAlchemy 2.x 管理；`src/agent_relay` 不直接导入 sqlite3 或使用其 Connection/Row/异常类型。SQLite 驱动和历史迁移 SQL 的存在不视为违例。
- A02：Repository 按房间资源、消息、投递和上下文能力划分；应用/领域不导入 SQLAlchemy，不透传 ORM/Session/SQL 表达式，查询返回现有业务值；无仅转发的通用 CRUD 层。
- A03：HTTP 事务继续惰性开启、共享请求写会话、响应开始前提交；错误、异常和提交失败正确回滚、释放资源，提交失败不能先发送成功响应。仓储和 provider 不自行提交。
- A04：后台动作使用独立短事务；成员绑定、外部观测、Codex 清队列和投递保留数据库与 RPC 分段，WebSocket 等待不保留会话。外部失败不能伪装为数据库可回滚的原子操作。
- A05：保持当前 `queue_deleted_20261110` 结构与迁移链，支持该 head 的已有数据库；保留复合外键、唯一约束、软删除、时间时区、回执和关联顺序；运行时不调用 create_all 或隐式升级旧库。
- A06：并发消息序号、publication_id 幂等、规范化项目唯一性和活动成员约束不退化；首版保留等价的 SQLite 写锁机制，序号读取和消息插入在同一事务内。
- A07：业务更新和显式 room_events 写入同事务；失败共同回滚，事件游标、补取、重启读取和无变化时不产生重复事件的行为保持。
- A08：有效队列与历史投递的区别、消息范围清空、全部分页、removedMessages 计数和 clear_codex 可选清理保持；状态条件写入保留删除标记与原回执，不自动重发或重试未知结果。
- A09：上下文可见性、字面关键词、双向分页、提供记录和位置单调推进保持；实际结果、提供记录、位置与对应事件同事务。
- A10：运行时 CRUD 与动态筛选使用 SQLAlchemy 表达式，移除手写 SQL 字符串拼接；必要的 BEGIN/PRAGMA、rowid 表达式集中在 SQLite 方言边界并明确列举，不把原 SQL 换成 text() 作为完成依据。
- A11：Engine/会话工厂由进程装配并关闭；Session 不跨请求或并发动作共享，顺序跨线程收尾经过验证；同步访问、配置、文件锁身份及 CLI/MCP 使用方式保持。
- A12：更新受影响测试、夹具和架构说明，运行约定的纯业务、数据库并发、事务、查询、投递及接口回归和类型/lint/格式检查；证据记录实际版本、命令、结果与未运行项，默认单元测试通过不能替代集成验证。

## Workload assessment / 工作量评估

- 工作量：中等偏大。主要产物包含持久化基础、资源仓储、消息及查询、投递条件写入、上下文复合操作和入口集成，均有可分别审查的结果。
- 复杂度：较高。现有单一 Store 同时承担资源工厂、事务、映射和多个能力，且测试夹具直接使用连接，迁移涉及契约及装配配套调整。
- 风险：较高，集中在写锁/序号、Session 隐式事务、时间映射、条件更新和事件原子性；必须保留有意义的并发及故障测试。
- Review 上下文：现有架构说明、请求事务中间件、RoomStore/DeliveryStore/MemberContext 契约、当前基线迁移及相关 integration 测试。
- 结论：建立六个 task。基础契约集中在首节点冻结，局部实现按依赖推进，最后统一切换入口并移除旧实现；拆分用于交付审查，不预设并行执行。

## Decisions / 决策

- 采用 SQLAlchemy 2.x ORM 与表达式 API；保留现有 Pydantic 业务值和专用查询契约。
- 首版不变更数据库结构，rowid 等少量方言依赖集中隔离，不宣称已经支持其他数据库。
- 事务由入口切面或独立短动作拥有；同一请求或用例内的仓储共享事务，不按模块引入专用 UoW 或分割提交，应用层不接触 Session。

## Risks / assumptions / 风险 / 假设

- 不使用默认 Session.begin 替代 BEGIN IMMEDIATE 的语义，也不因启用 ORM 将只读检查延长到 RPC 之后。
- 现有基线以外的旧 revision 本就没有自动升级链；本任务只承诺当前 head 数据兼容。
- 首版映射与既有 SQL-first Alembic 双重描述结构，需检查约束一致性；不自动生成或重写迁移。
- 当前工作区独立修改由原任务维护；后续实施前核对实际 HEAD、文件归属和前置交付版本。
