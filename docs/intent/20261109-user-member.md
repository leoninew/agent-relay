# 意图：固定用户成员与统一消息路由
最后修改时间: 2026-11-09 16:06:17

## 审查状态

Accepted

## 背景与目标

当前用户以空发送者 ID、YOU 头像和独立 consoleRecipient 字段出现，成员却必须绑定 Codex 会话。将用户纳入真实成员模型，统一称为“你”，并明确成员身份与会话投递的边界。

## 场景与验收

- A01：新建和已有房间都包含固定用户成员，名称为“你”，不显示管理员身份，不绑定会话，不提供删除或编辑入口。
- A02：用户发言、头像、引用回复、成员筛选、接收人展示统一使用“你”；发给用户的消息使用正常的 @ 成员表示。
- A03：Agent 可使用成员目录中的用户 ID，通过普通 mentionedMemberIds 单独发给“你”；即使只有一位 Agent，发布也有效。
- A04：仅发给“你”时不生成 Delivery，不进入 Codex queue；同时发给用户和 Agent 时，仅向 Agent 生成投递，排除发送者并保持去重。
- A05：会话发现与状态刷新不处理用户成员；用户始终可作为接收对象，不受 Codex 会话可用性影响。
- A06：已有消息、发布幂等性、话题订阅、外键和投递记录迁移后保持有效，旧用户消息与 consoleRecipient 消息转换为成员引用。

## 范围与非目标

修改成员模型、数据库迁移、消息路由、成员目录、CLI/MCP 契约及相关前端；不实现多人登录、权限系统或用户已读回执，不改 Node 环境和独立浏览器 MCP 项目，不扩展 README。

## 工作量评估

工作量中等，复杂度集中在同一成员契约贯穿存储、路由和界面，风险集中在历史数据迁移和误生成会话投递。相关修改需要共同集成，保持单任务，由当前会话串行实施。使用开发库的实际升级和外键检查核对 schema，使用业务回归覆盖队列隔离；按用户后续要求，不新增迁移单元测试。不建立独立 task。

## 决策与假设

用户为房间内固定的人类成员，Agent 为绑定会话的成员；成员类型用于选择投递方式，不向界面暴露管理员称谓。用户可查看房间全部消息，显式 @ 仅表示接收对象，不是查看消息的前提。
